Title: Scoped Single-Threaded Async
Author: Flecha Project
Type: Standards Track
Topic: Language
Status: Accepted
Created: 2026-11-15
Target: Flecha 0.4
Implementation: Complete
Release-Impact: Blocker

Abstract
--------

Specify scoped asynchronous tasks on one executor thread, with a general
model for suspendable computations rather than an I/O-specific compiler
feature. Retain Flecha's explicit ownership, exclusive mutable borrowing,
and deterministic cleanup responsibilities.

The agreed Flecha 0.4 direction is scoped, single-threaded async. The selected
policies below supersede earlier recommendations. Checked result destructuring,
compiler-managed generated frames, the versioned compiler/runtime ABI, and an
`async main` entry wrapper form the initial executable boundary. Public
language-level low-level future APIs remain deferred until their source
contract is accepted.

Flecha 0.4 is not complete until generated-frame borrow validation, the public
compiler/runtime ABI, production `NativeCompiler` and `async main` integration,
end-to-end execution and diagnostic coverage, and the interoperability boundary
are complete. The former execution gate was removed only after those criteria
were delivered. See ../async-design.md for the implementation guide and current
status.

Decision status
---------------

Selected foundation:

- Single-threaded execution of scoped tasks; shoot creates no OS thread.
- async functions and explicit postfix .await.
- Unawaited high-level async calls are errors, except explicit task creation.
- shoot and >>- are equivalent spellings for child-task creation.
- High-level async and low-level future/polling control share one model.
- Channels belong in the standard library over general waiting primitives.
- Live borrows survive suspension and cancellation requests; safe retirement
  and cleanup must precede loan release.
- Joining releases capture loans not retained by a result or pending operation.
  Borrowed results retain their origins after task completion.
- Compiler-managed stable frame storage supports safe borrowing of locals
  across suspension without a public Pin-like mechanism.
- Unsafe preserves checked-borrow rules and does not permit synchronous
  functions, ordinary defer, or teardown to suspend.

Additional approved decisions:

- Each lexical block owns children directly spawned in that block. Normal
  fallthrough joins them; return and exiting break/proceed cancel and drain
  unfinished children, innermost scope first, before captured locals die.
- Same-block transfers do not clean up that block. Cross-scope jumpto is
  initially rejected inside async functions. Results are consumed once;
  unconsumed results are destroyed during scope cleanup.
- Async main is the only initial synchronous entry. Async blocks, indirect
  async calls, async interface dispatch, and async extern functions are deferred.
  Synchronous defer and teardown still work inside async functions.
- Shoot requires a direct async call. Shoot and contiguous >>- are operand
  prefixes; both x >> -y and x>>-y retain shift/minus parsing. Postfix await
  permits immediate joining with (shoot f()).await.
- Shoot only queues; runnable tasks are FIFO, duplicate wakes coalesce, and
  callbacks enqueue without reentering task code.
- Cancellation is observed before first execution and at await/scope-drain
  boundaries. Operations acknowledge safe retirement before frame cleanup.
  Ordinary error values do not cancel siblings or propagate automatically.
- Recursive async calls are required. Frame allocation must be recoverable;
  allocation alone must not force every async declaration to be crashable.
- Child creation is also recoverable, superseding the earlier crashing
  allocation policy. An async-specific AsyncResult<T> wrapper is not selected.
- Fallible creation and checked non-void await require immediate destructuring:
  child, err := shoot f(); or value, err := f().await. A value binding is
  uninitialized on failure and usable only after its error is proven none.
  No dummy T is constructed and ordinary returned errors are not flattened.
- Void await binds only an execution error: err := operation().await;
  none means success. operation().await?; and child.await?; are valid void
  statements with no completed value.
- .await? yields completed T on success and forwards execution failure after
  cancellation, draining, and cleanup. Ordinary errors within T stay within T.
- Explicit awaits are required wherever child execution failure could otherwise
  go unobserved at normal scope exit; no implicit failure propagation is added.
- Reserve frame and scheduler admission resources before evaluating arguments
  or method receivers. Reservation failure runs no argument effects, transfers
  no ownership, and publishes no handle. Later execution failure does not roll
  back effects. Prepared-argument restrictions remain until lowering supports
  this allocation-first ordering.
- Root allocation failure reports a diagnostic and exits nonzero before user
  code runs or ownership transfers.
- A private C++ polling/wakeup ABI is approved as an intermediate stage only.
  Public Flecha high-/low-level interoperability remains required.

Deferred beyond the initial Flecha 0.4 executable boundary:

- Public future/polling/wakeup APIs and explicit low-level future access.
- Portable backends and explicit cancellation/yield APIs.

Acceptance fixes the high-level single-threaded contract and its v0.4 release
gate. It does not imply that executable async is supported before all completion
criteria pass. See ../async-design.md for the current
implementation/deferred-work table.

Motivation and boundary
-----------------------

A useful first experiment is servicing multiple network connections while
waiting for sockets and timers on one thread. This is a proposed validation
workload, not a decision to introduce a particular networking API.

Only one task executes Flecha code at a time. Suspending one task allows another
to run. This provides concurrency of waiting, not parallel execution of CPU
work. A blocking call or computation that never yields can stall every task.

Threads, work stealing, detached tasks, shared-memory parallelism, atomics,
and a general concurrent memory model are outside this first design. The
concurrency gate in ../memory_safety_invariants.md remains in force. Acceptance
would need to document precisely the single-threaded subset that is enabled;
the implementation remains fail-closed until that subset is validated.

Terminology
-----------

A task is an execution that can suspend and later resume. Its frame stores
the state needed across suspension, including live owned values and borrows.

A task scope owns its child tasks and bounds their execution lifetimes. A
child may own another task scope. No child execution escapes its owning scope.

An executor selects ready tasks and handles wake notifications from operations.
A join waits for a child's completion. Draining a scope waits until every
child and its pending operations have finished the required cleanup.

Cancellation is a cooperative request to stop unfinished work. It is not
permission to free a live task frame or borrowed I/O buffer immediately.

Selected high-level syntax
--------------------------

Suspendable functions use an async modifier. Their written return type is the
completed value type. Await must also represent recoverable execution failure;
its selected surface is immediate checked destructuring. The examples below
show the approved contract. Postfix .await
waits for a result and may suspend the current task; an immediately available
result need not suspend.

    async i32 calculate() {
        return 42;
    }

    async i32 example() {
        value, err := calculate().await;
        if err != none { return 1; }
        return value + 1;
    }

For the initial high-level surface, calling an async operation requires an
async function. An ordinary async call without .await is a compile error:

    value, err := calculate().await; // Check err before using value.
    calculate();                    // Error: unawaited async call.

Explicit child-task creation is the exception: shoot schedules an independent
child within the owning task scope and produces a fallible task handle. The symbolic
prefix >>- is an exact synonym, not a different scheduling or ownership mode.
These are alternative spellings of the same expression:

    first, err := shoot calculate();
    first, err := >>- calculate();

The handle can be awaited to join the child and obtain its completed result:

    async i32 combined() {
        first, firstError := shoot calculate();
        if firstError != none { return 1; }
        second, secondError := >>- calculate();
        if secondError != none { return 1; }
        a, aError := first.await;
        if aError != none { return 1; }
        b, bError := second.await;
        if bError != none { return 1; }
        return a + b;
    }

Both children are scheduled before either is joined. Awaiting their handles
in sequence does not make their execution sequential. Neither spelling implies
another OS thread or detached execution. A child is queued, never run inline.

An ordinary call followed by .await does not independently schedule a child.
For example, calculate().await followed by another calculate().await performs
those computations sequentially within the current task. Explicit task creation
provides independent scheduling; awaiting a task handle joins that child.

Each lexical block owns directly spawned children. Async main is the initial
entry; async blocks are unsupported. Shoot and contiguous >>- are operand
prefixes; infix x >> -y and x>>-y remain shift/minus. Both child-creation
spellings have identical semantics and diagnostics. Fallible result/handle
bindings use immediate checked destructuring. The selected keyword is shoot, replacing spawn; >>-
remains its synonym. Child creation is recoverable, just like direct-await
frame allocation.

General high-level and low-level model
-------------------------------------

The intended direction is to support both compiler-managed async functions and
low-level control of futures and polling through one execution contract. That
contract is not restricted to sockets: messages, application events, external
completions, and computations split into resumable steps are also use cases.

Ordinary callers should not need to implement polling or handle wake tokens.
Library authors should be able to supply awaitable operations without adding
compiler primitives for each operation. The exact public future API and wakeup
protocol remain open, as does the explicit low-level mechanism for managing a
future without violating the high-level unawaited-call rule.

The interoperability goal is that a library-defined future can be awaited by
high-level code, and compiler-generated async work can be managed through the
low-level contract. These are two ways to express work, not separate runtimes.
Low-level access must preserve the same ownership and cleanup guarantees.

A candidate protocol, expressed as pseudocode rather than Flecha declarations,
is:

    poll(context) -> Ready(result) | Pending | Cancelled | AllocationFailed

Polling is synchronous and nonblocking. Pending requires a valid way to arrange
another attempt when progress becomes possible; it is not a request for a busy
loop. Completion includes the operation's ordinary result or error values.
The runtime protocol distinguishes these four outcomes. The exact public
Flecha source protocol remains open. No public Future, Poll,
Context, or wake-handle type name is selected by this pseudocode.

The generic progression is: running work becomes waiting, a notification makes
it runnable, and the executor resumes it. Execution state remains alive while
waiting. A task may repeat this sequence many times before completing. An OS
event is one possible notification source; another task or a library event can
also notify a waiter. Registration and suspension must not lose a notification
that arrives between checking the operation and becoming a waiter.

Channels are intended as standard-library abstractions over the same general
waiting and wakeup machinery, not channel-specific compiler operations. Their
endpoint types, allocation, capacity, closure, and error contracts need review.

No protocol can make arbitrary blocking code nonblocking automatically. Work
must offer notifications, support resumable steps, or execute elsewhere. A
worker-thread bridge would require a separate contract beyond this initial
single-threaded scope.

Selected lifetime policy
------------------------

Every lexical block owns children spawned directly within it. Normal
fallthrough joins them. Return and break/proceed that leave the block request
cancellation of unfinished children and drain them before local cleanup.
Multiple exited scopes drain from innermost to outermost. A transfer staying
inside a block does not clean up that block. Cross-scope jumpto is initially
rejected inside async functions.

Discarding a task handle never detaches execution or releases live borrows.
Joining consumes a result once; already-joined children need no further wait.
Unconsumed completed results are destroyed during scope cleanup. Ordinary
error values neither cancel siblings nor propagate automatically. Returning
an error follows the same early-exit rules as any return.

Await now needs a recoverable execution-failure outcome distinct from the
function's completed T, including when deeper recursive frame creation fails.
Immediate checked destructuring and explicit .await? failure forwarding are
selected. Void await returns only an error, with none meaning success. Normal
scope exits with potentially unobserved child execution failures are rejected.
There is no implicit exception propagation selected by this document.
Ordinary returned errors use prefix try call(), requiring a compatible final
error field in the enclosing completed result. This is distinct from .await?,
which forwards execution failure independently of the written completed type.

Cancellation is observed before first execution and at await/scope-drain
boundaries. A pending operation must acknowledge safe retirement before its
frame is destroyed. Cancellation remains cooperative: early exit can wait
indefinitely for children to reach observation points and finish cleanup.
Explicit user cancellation APIs and cancellation masking remain deferred.

Only suspendable code performs async draining. Ordinary synchronous deferred
calls and teardown still work inside async functions; they cannot suspend.

Ownership and suspension requirements
-------------------------------------

The existing rules in ../memory_model.md and ../memory_safety_invariants.md
provide the safety constraints for any proposed implementation:

- A borrow held by a suspended task remains live. Single-threaded scheduling
  does not grant the parent or another child conflicting access.
- A parent cannot move, replace, destroy, or invalidate storage while a child
  or an outstanding operation borrows it.
- Multiple read-only captures can coexist. Overlapping mutable captures, or a
  mutable capture overlapping a read-only capture, require rejection.
- A child's execution cannot outlive its scope. Captured storage must survive
  draining, including cancellation and nested-child cleanup.
- Returning a borrowed result does not erase its origin. Completing the task
  alone cannot release a borrow still carried by that result.
- Moving an owner into a task transfers cleanup responsibility exactly once.
  Task creation failure must have a defined ownership outcome.
- Frame relocation cannot invalidate references into that frame. The compiler
  must ensure valid storage and stable addresses where required, including for
  immovable values and references to task locals. Safe async code must not need
  a public Pin-like mechanism merely to borrow locals across suspension.

The initial checker should reuse Flecha's conservative region model. Proving
disjoint array ranges is not a prerequisite. An explicit join releases capture
loans when neither the returned value nor an outstanding operation retains them.
Borrowed results preserve their origins after completion. A cancellation request
alone never releases loans: safe retirement and cleanup must finish first.

Unsafe does not disable existing checked-borrow rules, authorize dangling
pointers, or make a synchronous function suspendable. Raw-pointer and backend
implementations must uphold storage lifetime, aliasing, address stability, and
callback retirement through both completion and cancellation.

Cleanup and external operations
-------------------------------

Child cleanup has to finish before cleanup invalidates its captured storage.
Merely appending a join after existing local destruction is insufficient.
Conversely, retaining a reference to a local that has already left its own
scope is invalid even if the enclosing task scope remains active.

Existing relative ordering of ordinary owners and deferred calls should be
preserved wherever their lifetimes are valid. Child draining precedes cleanup
that could invalidate captured storage. Ordinary teardown and deferred calls
remain synchronous; this does not forbid existing cleanup mechanisms in async
functions. Tests must verify the resulting order.
Asynchronous protocol shutdown would need an explicit operation before final
synchronous resource release.

Cancellation of an I/O wait must ensure that neither the backend nor a late
notification can access released task storage or buffers. Readiness removal
and completion-based cancellation may require different runtime mechanisms.
Repeated notifications must be handled without duplicate or reentrant task
execution. Resuming a completed task or accepting a stale event for a reused
task slot must be prevented.

Foreign callbacks must not reenter suspended or running task code in a way
that violates exclusive access. Work performed by the OS does not authorize
concurrent Flecha callbacks. Backend buffer-access contracts need review even
when only one thread executes Flecha code.

Immediate process termination remains distinct from graceful scope exit. This
proposal does not add unwinding guarantees to existing fatal safety failures.

Behavioral examples -- notation only
------------------------------------

These are event sequences, not proposed Flecha syntax.

1. Normal completion:
   Parent creates a scope and starts two child operations. One suspends on a
   socket; the other completes. Parent reaches scope end. The scope waits for
   the first operation and drains before releasing captured storage.

2. Early exit, under the selected policy:
   Parent chooses to return while a child waits on I/O. It requests child
   cancellation. The backend makes the pending operation safe to retire;
   child cleanup finishes; parent cleanup and return can then finish.

3. Invalid overlapping access:
   Child holds a mutable borrow of a buffer and suspends. Parent reads or
   writes that buffer before the loan ends. Reject, despite one executor
   thread and despite the child not currently executing.

4. Invalid escape:
   Parent attempts to return an independently runnable child that borrows a
   local. Reject. No detached-task escape is part of this design.

5. Borrowed result:
   Child returns a view into a parent-owned buffer. Joining the child does not
   allow destruction or replacement of the buffer while the view is live.

6. Liveness limit:
   Child runs an infinite computation without yielding. Other tasks and scope
   cancellation cannot progress. Single-threaded async does not prevent this.

Compiler, runtime, and tooling consequences
-----------------------------------------

Before implementation, decide how the selected suspension syntax is represented
in callable types, generic constraints, interface dispatch, and diagnostics.
The high-level syntax does not select stackful versus state-machine execution,
nor does it settle the public low-level future protocol or task type names.

A compiler-transformed design would need frame liveness, borrow origins across
suspension, initialization and cleanup state, and all scope exit edges modeled
before lowering. A library-only design would still need to prove that its safe
API cannot bypass the ownership and lifetime requirements above.

The executor needs an explicit ownership boundary, readiness registration,
wakeup deduplication, task retirement, and a documented reentrancy policy.
Frame allocation, executor allocation, resource limits, and allocation failure
must be explicit in the eventual contract. No hidden thread pool is assumed.

Diagnostics should identify the capture, suspension or outstanding task, and
conflicting use. Analyzer navigation and hover should expose any eventual
suspension effects without claiming draft syntax is implemented.

Validation and implementation sequence
--------------------------------------

1. Resolve remaining policy and grammar questions; review ownership and cleanup traces.
   Accept a normative contract before enabling a safe language surface.
2. Prototype the chosen execution model with a deterministic test executor.
   Validate library-defined completions and high-/low-level interoperability,
   borrowed captures, results, nested scopes, and failure cleanup. Prove the
   model works without socket-specific compiler support.
3. Add timer and socket experiments with injected readiness and cancellation
   races. Check pending operations and storage retirement, not just output.
4. Exercise a bounded multi-connection service, slow clients, partial reads
   and writes, allocation failure, and shutdown with outstanding operations.
5. Complete diagnostics, analyzer support, backend qualification, and release
   documentation before describing async as supported.

Tests should cover every legal scope exit, repeated cancellation, simultaneous
completion and cancellation, nested scope draining, and unconsumed results.
Ownership tests should count destruction and deferred calls and verify their
order. Scheduling tests should explore multiple legal interleavings; tests
must not assume an ordering the final contract does not guarantee.
Both shoot spellings need equivalent semantic and runtime coverage. Negative
cases must include a bare async call and awaiting from a synchronous function
outside any future explicitly approved executor-entry construct. Completion
tests need ready-before-wait, notification-during-registration, repeated wakeup,
and cancellation-before-completion cases using synthetic events as well as I/O.

Alternatives and open decisions
-------------------------------

Always joining on every exit and requiring explicit joins on every exit were
considered. Lexical normal-exit join and early-exit cancel-and-drain were selected.
Crashing for every frame allocation was also considered; recoverable allocation
is now the foundation. A failed frame must not fabricate a T or force every
async function to be marked crashable. Root entry has the separately approved
diagnostic/nonzero-exit policy.

Detached tasks and multithreaded scheduling are deferred because they require
additional lifetime and sharing contracts. Blocking I/O behind an async-looking
API would not validate the intended overlap of waits.

Open decisions requiring review include:

- Low-level future access, polling, wakeups, and interoperability with .await.
- Explicit cancellation/yield APIs and interrupted operation contracts.
- First I/O surface and portable backend requirements.

The v0.4 implementation includes resumable lowering, cleanup state, aggregate
borrow/result tracking, analyzer integration, and executable tests. A private
runtime alone would not have satisfied these requirements.

Compatibility
-------------

The implementation reserves async and shoot and carries a versioned public C
compiler/runtime entry ABI over the private C++ executor. Await remains a
contextual postfix. Existing synchronous execution semantics and shift/minus
expressions are preserved. No language-level low-level future/result API is
finalized. Further syntax and API changes require review.
