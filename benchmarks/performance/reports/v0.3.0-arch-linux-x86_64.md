# Flecha v0.3 controlled performance reference

This is the curated controlled-host result for the versioned v0.3 workload
contract. It is preserved so v0.4 and later releases can run the same sources
and compare like with like. It is not a universal language ranking or an Ubuntu
CI regression baseline.

## Campaign identity

- Date: 2026-11-05
- Host: AMD Ryzen 5 8600G, 12 logical CPUs
- Platform: Arch Linux x86_64, Linux 7.1.8, glibc 2.44
- Samples: 11 measured after 3 warmups
- Per-process timeout: 120 seconds
- Runtime order: deterministic rotation by sample
- Flecha: `0.2.5-312-gace1b98-dirty`, native LLVM O2
- C: GCC 16.2.1, `-O2`
- Rust: rustc 1.98.1, `-C opt-level=2`
- Go: Go 1.27.1, ordinary optimized build
- Python: CPython 3.14.7

Command:

```sh
python3 tools/performance.py run \
  --flecha build-tests/flecha \
  --longbow build-tests/longbow \
  --std std/src \
  --build-dir /tmp/flecha-performance-final/work \
  --samples 11 --warmups 3 --timeout 120 \
  --output results.json --markdown results.md --svg results.svg
```

Every sample completed with the versioned expected checksum.

Flecha wins 1/4 assignments against C, 1/4 against Rust, 2/4 against
Go, and 4/4 against Python. The result is **B tier** because Flecha beats Rust
on the rounds assignment. That win is robust in this campaign: Flecha's P90 of
13.753 ms is below Rust's P10 of 14.079 ms, and also below C's P10 of
14.103 ms.

### Why rounds wins

Disassembly confirms that every native implementation uses hardware `rol`
instructions and that Flecha has no calls, allocations, bounds checks, or
overflow branches inside the hot loop. Flecha's register allocation preserves
separate intermediate left/right values and uses `lea` for the indexed add,
shortening the loop-carried dependency chain. GCC's C and Go overwrite their
accumulators in place. Rust unrolls two inherently serial rounds, adding
bookkeeping without exposing parallel work.

LLVM MCA's Zen 4 scheduling model estimates 503 cycles per 100 Flecha rounds,
603 for C, 603 for Go, and 1203 per 100 two-round Rust blocks: approximately
5.03 cycles per Flecha round versus 6.02–6.03 for the others. This static model
is not a hardware-counter measurement, but its predicted ordering agrees with
both controlled campaigns. It explains this assignment, not general language
performance.

## Non-scored collection diagnostic

| Assignment | Flecha | C | Rust | Go | Python |
| --- | ---: | ---: | ---: | ---: | ---: |
| collections_growth | 6.774 (6.395–7.072) | 4.715 (4.333–5.072) | 4.837 (4.507–5.437) | 7.907 (7.521–8.593) | 90.109 (87.491–92.469) |

The reserved workload leaves Flecha 27.0% behind Go. The default-growth
diagnostic puts Flecha 14.3% ahead, with Flecha's P90 below Go's P10. Direct
`GODEBUG=gctrace=1` diagnostics observed one Go collection in the reserved case
and seven in the growth case. The result points to fallible push/control-flow
cost on the reserved fast path, not a general disadvantage of Flecha's no-GC
ownership model.

## Cross-host confirmation

The pinned Ubuntu 24.04 GitHub runner campaign independently produced B tier:
Flecha's rounds median was 19.189 ms versus Rust at 23.751 ms and C at
21.182 ms. Flecha again won 1/4 against C, 1/4 against Rust, 2/4 against Go,
and 4/4 against Python. Reserved collections were effectively tied with Go
(26.234 ms versus 25.921 ms, with overlapping distributions), while the
non-scored default-growth diagnostic favored Flecha by 14.196 ms to 34.167 ms.
The exact Flecha wall/RSS values and pinned toolchains are preserved in
`benchmarks/performance/baselines/ubuntu-24.04-x86_64.json`.
